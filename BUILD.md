# Building SymonSayLearn

Two ways to build this, and they answer different questions.

| Path | Answers | Time | Use when |
|---|---|---|---|
| **Host build** | "does it run here, now?" | minutes | developing, proving a change |
| **BitBake build** | "does it install from packages into a clean root?" | hours | releasing |

A host build proves behaviour. A BitBake build proves the packaging. Neither
substitutes for the other, and a release needs both.

---

## 1. What you get

| Surface | Bind | Serves |
|---|---|---|
| Gateway | `127.0.0.1:9001` | the `/v1` Anthropic dialect: models, messages, count_tokens |
| Chat unit | `127.0.0.1:8802` | the engine behind the gateway |
| Web interface | `127.0.0.1:8812` | overview, registry, rack, three surfaces |

Three models, one per client surface: `symon-chat`, `symon-coder`, `symon-work`.

Nothing leaves the machine. Public reach, when wanted, is through the edge proxy and
the Cloudflare tunnel, never by binding an interface.

## 2. Prerequisites

### Generic, any host

| Need | Why |
|---|---|
| Linux, glibc | the estate targets glibc; musl is untested here |
| Python 3.12+ | the gateway is FastAPI on the estate's Python closure |
| ~30 GB free | weights are ~13 GB, node_modules ~350 MB, build trees the rest |
| A model checkpoint | **not shipped.** See §5 |

### Additionally, for a GPU build

| Need | Why |
|---|---|
| NVIDIA driver and a matching CUDA userspace | the chat unit runs weights on the card |
| VRAM ≥ weights + working set | see §4 for what that actually means |

## 3. Host build

The fast path. Builds nothing that is not already source; starts three processes.

### 3.1 The chat unit

```sh
work/runtimes/llm/hostrun/bringup-chat-unit.sh
```

This is a **ladder**, not one command, and §4 explains why. It tries configurations
in order and stops at the first that actually serves, recording which one in
`$SYM_RUN_DIR/logs/chat-unit-bringup.log`. Success means the port answers, not that a
log line looked hopeful.

Settings it honours, all with defaults:

| Variable | Default | Meaning |
|---|---|---|
| `SYM_MODELS_DIR` | `/home/google/symoneural-models` | weight store |
| `SYM_CHAT_PORT` | `8802` | bind port, the `chat` unit's registered port |
| `SYM_MAX_MODEL_LEN` | `16384` | served context window |
| `SYM_GPU_FRACTION` | `0.90` | fraction of the card the engine may claim |
| `SYM_CPU_OFFLOAD_GB` | unset | GiB of weights held in host RAM |
| `SYM_CHAT_ENGINE_VENV` | a host virtualenv | **see the barrier in §6** |

### 3.2 The gateway

```sh
# provision the credential first; it is never generated by tooling or an agent
mkdir -p -m 700 ~/.config/symoneural
(umask 077; openssl rand -hex 32 | tr -d '\n' > ~/.config/symoneural/gateway-9001.key)
chmod 600 ~/.config/symoneural/gateway-9001.key

cd work/runtimes/api/app
PYTHONPATH=$PWD python3 -m symoneural_api.gateway
```

Unconfigured fails closed: with no key file, every authenticated route answers 500
naming the missing path. It does not default to open.

### 3.3 The web interface

```sh
cd work/runtimes/web/app
pnpm install           # see §6: the framework is not acquired
pnpm build
pnpm start             # 127.0.0.1:8812
```

### 3.4 Prove it

Do not trust a process list. Prove the contract:

```sh
KEY=$(cat ~/.config/symoneural/gateway-9001.key)

curl -fsS http://127.0.0.1:9001/health                      # {"status":"ok"}
curl -fsS -H "authorization: Bearer $KEY" \
     'http://127.0.0.1:9001/v1/models?limit=1000'           # three rows, each with a tier

curl -fsS -X POST http://127.0.0.1:9001/v1/messages \
  -H "authorization: Bearer $KEY" \
  -H 'anthropic-version: 2023-06-01' -H 'content-type: application/json' \
  -d '{"model":"symon-chat","max_tokens":1,"messages":[{"role":"user","content":"."}]}'
```

The last one is the exact request a conforming client's connection test sends. A 2xx
with `content` as an **array** is the pass condition. Reproduce it before anyone
presses a Test button.

## 4. Hardware profiles

The one thing that actually varies between machines is how the mixture-of-experts
weights get onto the card. Read the profile that matches yours.

### 4.1 NVIDIA, compute capability 9.0 to 10.x (Hopper, datacenter Blackwell)

The Triton mixture-of-experts path is available. Weights load in their packed form,
no repack, so peak memory during load is close to the checkpoint size.

```sh
SYM_GPU_FRACTION=0.90 SYM_MAX_MODEL_LEN=32768 work/runtimes/llm/hostrun/serve-chat-unit.sh
```

### 4.2 NVIDIA, compute capability 12.x (sm_120, consumer Blackwell) — the reference host

**The Triton path is excluded by an explicit range check**, measured in
`fused_moe/experts/gpt_oss_triton_kernels_moe.py`:

```python
# covers Hopper SM90 and Blackwell SM100, excludes SM120
return cap is not None and (9, 0) <= (cap.major, cap.minor) < (11, 0)
```

Installing `triton_kernels` does **not** help; the gate is the capability, not the
module. The remaining path is Marlin, which **repacks** the weights into its own
kernel format during load, and that repack peaks above the checkpoint size.

Measured on this host with a 12.82 GiB checkpoint and 15.56 GiB of VRAM:

| Utilisation | Context | Offload | Result |
|---|---|---|---|
| 0.93 | 16384 | — | refused before loading: free 14.23 GiB < requested 14.47 GiB |
| 0.90 | 16384 | — | out of memory inside the repack, short by 2.4 MiB |
| 0.917 + `expandable_segments` | 16384 | — | out of memory |
| 0.917 + `expandable_segments` | 8192 | — | out of memory, short by 1.6 MiB |
| **0.917 + `expandable_segments`** | **16384** | **3 GiB** | **serves** |

A miss of 2.4 MiB is fragmentation, not a shortfall, which is why the ladder's first
rung only changes the allocator and costs nothing. Working configuration:

```sh
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
SYM_GPU_FRACTION=0.917 SYM_MAX_MODEL_LEN=16384 SYM_CPU_OFFLOAD_GB=3 \
  work/runtimes/llm/hostrun/serve-chat-unit.sh
```

Result: weights 10.5 GiB on card, KV cache 3.12 GiB, 108,294 tokens, 6.6x concurrency
at 16k. **The KV pool is far larger than one request needs**, so the served window can
be raised well above 16384 without more VRAM. Raise `SYM_MAX_MODEL_LEN` and re-measure.

Free the card first if you can. The desktop compositor held ~1.0 GiB on this host; a
headless session recovers it and may remove the need for offload entirely.

### 4.3 Less VRAM than the checkpoint

Raise `SYM_CPU_OFFLOAD_GB` until it loads. Every offloaded gigabyte crosses PCIe on
every token, so throughput falls; it is a way to run, not a way to run well. With
94 GiB of host RAM the ceiling is the patience of whoever is waiting.

### 4.4 CPU only

The checkpoint fits in host RAM comfortably. Expect memory-bandwidth-bound
throughput, and on a CPU without AVX-512 or AMX — like the reference host — expect it
to be usable for batch work and not for interactive chat. **No tokens-per-second
figure is quoted here because none was measured on this host.**

### 4.5 AMD

Untested here. The engine's own device gate accepts gfx9 and gfx1x families, so the
Triton path may be available where it is not on sm_120. Treat §4.1 as the starting
point and measure rather than assuming.

## 5. Models are not shipped

Nothing in this repository installs a weight file, and `.gitignore` denies the shapes
by extension and by directory. The runtime reads `SYM_MODELS_DIR` at run time.

Reasons, all three load-bearing: weights are multiple gigabytes, their licences
differ per model and travel with them, and a repository that is published once is
forked, cached and archived whatever it does later.

Reference host layout:

```
/home/google/symoneural-models/gpt-oss-20b/     12.82 GiB, MXFP4 MoE
/home/google/symoneural-models/image/           FLUX.1-schnell set
```

Verify a checkpoint before serving it — size alone is not integrity, because a
resumed download onto a corrupt prefix yields the right length:

```sh
python3 - <<'PY'
import json, os, struct, sys
d = "/home/google/symoneural-models/gpt-oss-20b"
idx = json.load(open(f"{d}/model.safetensors.index.json"))
total = 0
for f in sorted(set(idx["weight_map"].values())):
    p = f"{d}/{f}"; size = os.path.getsize(p)
    with open(p, "rb") as fh:
        n = struct.unpack("<Q", fh.read(8))[0]; hdr = json.loads(fh.read(n))
    payload = max(v["data_offsets"][1] for k, v in hdr.items() if k != "__metadata__")
    print(f, "consistent" if 8 + n + payload == size else "INCONSISTENT")
    total += payload
print("index total:", idx["metadata"].get("total_size"), "sum:", total,
      "MATCH" if idx["metadata"].get("total_size") == total else "MISMATCH")
PY
```

## 6. BitBake build

The packaging proof, and what a release is cut from.

```sh
bitbake symoneural-image-learn
```

Produces a rootfs tarball assembled by opkg **from the package feed**: no source
tree, no devtool workspace, no pip, no build frontends. That is the point — it proves
the runtime installs from packages rather than from the tree it was developed in.

| Recipe | Role |
|---|---|
| `packagegroup-symoneural-learn` | the composition: api + llm + common + glue |
| `symoneural-learn` | bring-up scripts and `SOURCE-TREE` |
| `symoneural-image-learn` | the proof image |
| `symoneural-learn-web` | the web interface — **blocked, see below** |

Before editing any recipe, check no cooker is live and read the exit code directly:

```sh
work/tools/edit-guard; rc=$?
```

### Barriers, recorded rather than worked around

**The web interface cannot be built by BitBake.** Next.js, React and Node.js are not
acquired into this estate: `upstream/web/` holds `workerd` and `workers-sdk` only, and
no recipe provides a target Node interpreter. The host build in §3.3 works because it
installs from the public npm registry, which is how Next.js is consumed but is **not**
acquisition — that tree is not pinned, not committed, and not verifiable against an
upstream commit. `symoneural-image-learn` excludes the package by design so the image
still builds. Three acquisitions unblock it, listed in the recipe header.

**The chat unit's engine is a substitution.** It is an acquired upstream build run
from a host virtualenv, not `symoneural-llm`, governed by rules section 3.10. Both
estate paths are blocked: `symoneural-llama-cpp` is configured
`LLAMA_BUILD_SERVER:BOOL=OFF` and produces no server, and the `symoneural-vllm` recipe
stops after `do_compile` with no packaging. Replacing it is the next phase. The
gateway is written so the cutover is a change of one address: `worker.py` reads
`SYM_CHAT_URL` and nothing above it knows which engine answers.

## 7. Traps this build has already paid for

Each of these cost a debugging session. They are here so the next one is shorter.

**`set -u` kills `oe-init-build-env`.** It references unset variables internally. The
symptom is the misleading part: an empty build log and `rc=1` with zero ERROR lines,
because the build never started.

**`addtask foo` binds to a function named `do_foo`.** A task function without the
`do_` prefix is silently never bound, and "passes" forever.

**`git archive` honours `.gitattributes export-ignore`.** An export is not always a
full copy of the worktree, so `LIC_FILES_CHKSUM` entries naming an ignored path fail
`do_unpack` permanently.

**An empty `PYTHONPATH` entry means the current directory.** A trailing colon put a
package directory ahead of the stdlib, and the error named a completely different
module.

**`bb.fatal` in an anonymous `python () { }` block fails every build in the layer**,
not just that recipe, because BitBake parses every recipe on every build. A recipe
that cannot be satisfied must still parse cleanly and fail in a task.

**`pkill -f 'vllm serve'` matches the shell that runs it**, because the pattern is in
that shell's own command line. Use `pkill -f '[v]llm serve'`.

**A liveness probe that fires before the thing can be alive measures its own timing.**
A bring-up check using `pgrep` five seconds in killed a rung that went on to load the
model successfully 36 seconds later. Give startup a grace period before absence counts
as failure.
