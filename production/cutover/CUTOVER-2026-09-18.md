## What it is not

- Not the harmony/reasoning parser: the raw completion path (no chat template) is garbage too.
- Not the cutile path: that is a cargo feature the build never enabled.
- Not a load failure: weights map to the card, the server answers, tokens are produced at
  166 tok/s (engine-side `avg_compl_tok_per_sec`).

## Suspects, in order

1. The MXFP4 GEMM kernels (`mistralrs-quant/kernels/mxfp4/mxfp4_gemm_wmma.cu`, bf16 WMMA
   fragments, LUT dequant) miscomputing on compute capability 12.0 with the 13.4 toolkit — the
   allowlist we patched past exists for a reason; 13.4 + consumer Blackwell is an untested pair
   upstream.
2. The paged-attention kernels with per-head attention sinks on this card.
3. Less likely: a dtype selection (`DType selected is BF16`) interacting with the MXFP4 experts.

## Next tests (each one variable)

1. **CPU-only decode of the same build** (`--cpu`, port 18802, 8 tokens) — if the text is sane,
   the model code and dequant are right and the defect is in the GPU kernels. Running at the
   time of writing; result appended below.
2. **ISQ 4 on the GPU** (`--isq 4`: dequantise MXFP4 → requantise to a 4-bit format whose CUDA
   kernels are mature; ~11 GB) — if sane, the native MXFP4 kernels are the culprit and ISQ 4 is
   a usable interim engine (needs a cutover window; ~42 GB host RAM during load).
3. **Paged attention off at 16k** (`--paged-attn off --max-seqs 1`) with a raw completion — if
   sane, suspect 2 is the culprit.
4. Rebuild with the toolkit the upstream allowlist does accept (13.3) if the host toolkit can
   be installed beside 13.4 — removes the patch from the equation.

## Test 1 result — CPU-only decode (08:31)

`--cpu`, port 18802, same binary, same checkpoint directory: `"The capital of France is"` at
temperature 0 → **`'(in the end, as alluded'`** (8 tokens, 0.67 tok/s on CPU). Garbage on the CPU
path as well. The substitution engine on the same files: `' Paris."…'`, and with a 512-token
budget a thinking block followed by a text block.

**Revised isolation:** the defect is in the engine's model implementation for this checkpoint at
pin `d5ae0f18` (shared by the CPU and CUDA paths — dequantisation, attention with sinks and
sliding window, or rotary scaling are the candidates), **not** in the sm_120a kernels and not in
the 13.4 toolkit. Suspects 1–2 above are withdrawn; test 2 (ISQ) and test 3 (paged-attention
off) would not separate anything and are dropped. Test 4 (rebuild with 13.3) is unnecessary.

**Next:** check upstream for a fix after the pin (issues and the history of the model file);
if one exists, re-pin forward — provided the commit is not August-dated — rebuild (43 min) and
repeat the cutover ladder from rung 2, which is known to fit.

Also observed, both engines: at 48 tokens the answer is a thinking block only — this
checkpoint reasons before it speaks. Not a defect. And the model names its upstream vendor
when asked what it is; a per-card default system prompt is the product-side answer (recorded,
not built).
